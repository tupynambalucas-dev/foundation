# Building and Testing Custom WSL2 Distributions

A hands-on tutorial for building the `tupynambalucas-dev` and `tupynambalucas-dev-cluster` WSL2 rootfs archives locally using Docker Buildx and testing them with native WSL import mechanics.

---

## Overview

In production, distribution archives (`.wsl`) are compiled in GitHub Actions CI/CD pipelines via `.github/workflows/release.yml`. However, during active development or when testing kernel modules, systemd configurations, and pre-installed packages, you can build and test distributions locally.

By the end of this tutorial, you will:
1. Understand the multi-stage Dockerfile architecture powering `.wsl` rootfs builds.
2. Build `output/tupynambalucas-dev.wsl` locally using Docker Buildx.
3. Compute the SHA-256 integrity hash required for catalog registration.
4. Manually import and test the distribution in WSL2.
5. Validate systemd masking and OOBE script execution.

---

## Prerequisites

- **Docker Desktop** (or Docker Engine in a Linux VM) with `buildx` enabled.
- **Windows 11 / Windows 10** with WSL 2.4.4+.
- PowerShell 7+ or Bash terminal.
- Cloned copy of the `tupynambalucas-dev/workstation` repository.

---

## Step 1: Inspect the Multi-Stage Dockerfile

Open `distributions/base/Dockerfile`. The build relies on a two-stage process:

1. **Stage 1 (`builder`)**: Starts from `ubuntu:devel` (Ubuntu 26.04 LTS), installs base packages, masks conflicting systemd units via `distributions/shared/systemd-mask.sh`, and stages OOBE scripts into `/usr/lib/wsl/`.
2. **Stage 2 (`rootfs`)**: Starts `FROM scratch` and copies only the cleaned rootfs (`COPY --from=builder / /`), ensuring no intermediate Docker build cache layers or dangling metadata remain.

---

## Step 2: Build the Rootfs Archive with Docker Buildx

Create a local output directory:

```bash
mkdir -p output
```

Execute the Buildx command targeting the `base` distribution:

```bash
docker buildx build \
  --output type=tar,dest=output/tupynambalucas-dev.wsl \
  -f distributions/base/Dockerfile \
  .
```

For the Kubernetes cluster distribution (`cluster`):

```bash
docker buildx build \
  --output type=tar,dest=output/tupynambalucas-dev-cluster.wsl \
  -f distributions/cluster/Dockerfile \
  .
```

Buildx streams the filesystem directly into a single uncompressed tar archive (`.wsl`).

---

## Step 3: Compute the Cryptographic SHA-256 Digest

Modern WSL catalog manifests require an integrity checksum formatted with a `0x` hexadecimal prefix.

### On Windows PowerShell:

```powershell
$hash = (Get-FileHash output\tupynambalucas-dev.wsl -Algorithm SHA256).Hash.ToLower()
$formattedHash = "0x$hash"
Write-Host "SHA-256: $formattedHash"
```

### On Linux / WSL:

```bash
HASH=$(sha256sum output/tupynambalucas-dev.wsl | awk '{print $1}')
echo "SHA-256: 0x${HASH}"
```

Record this value for catalog registration or local CLI installation verification.

---

## Step 4: Test Local Installation via gh-tl CLI

The `tl distro install` command provides a dedicated `--from-file` parameter to test local archives before publishing:

```bash
gh tl distro install tupynambalucas-dev \
  --from-file output/tupynambalucas-dev.wsl \
  --sha256 "0x<your-computed-hash>"
```

The CLI verifies that the computed hash matches your `--sha256` parameter before invoking `wsl.exe --install --from-file`.

---

## Step 5: Alternative: Manual Import with wsl.exe

You can also test the archive directly using native `wsl.exe --import`:

```powershell
# Create destination directory for VHDX
New-Item -ItemType Directory -Force -Path "$env:LOCALAPPDATA\WSL\test-distro"

# Import rootfs into managed VHDX
wsl.exe --import test-distro "$env:LOCALAPPDATA\WSL\test-distro" output\tupynambalucas-dev.wsl --version 2
```

Launch the test instance:

```bash
wsl.exe -d test-distro
```

---

## Step 6: Validate Runtime Hygiene & Systemd Masking

Inside the running distribution, verify the critical runtime invariants:

```bash
# 1. Verify systemd is active
systemctl is-system-running
# Expected output: running or degraded (not offline)

# 2. Verify conflicting units are masked to /dev/null
systemctl status systemd-resolved.service
# Expected output: Loaded: masked (Reason: Unit systemd-resolved.service is masked.)

# 3. Verify DNS is automatically handled by WSL
cat /etc/resolv.conf
# Expected output: # This file was automatically generated by WSL.

# 4. Verify developer account
whoami
# Expected output: tupy
```

---

## Step 7: Clean Up Test Instance

After validating changes, terminate and unregister the test distribution:

```bash
wsl.exe --terminate test-distro
wsl.exe --unregister test-distro
```

Delete the local build artifact:

```bash
rm -f output/tupynambalucas-dev.wsl
```
